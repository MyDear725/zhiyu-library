# 意图感知座位匹配升级设计

日期：2026-08-23

状态：用户已批准
项目：智域图书馆黑客松第三版

## 1. 背景与目标

当前版本已经具备座位地图、预约和学习意图入口，但演示链路中存在三个关键断点：页面日期写死为 `2026-08-20`，座位读取不区分日期和时段，区域推荐由固定映射决定而不是由实时空位与聚合需求共同决定。

本次升级只聚焦一个可在约 90 秒内讲清楚的端到端故事：

> 用户输入学习意图 → 系统结合场景适配、当前时段空位率和匿名聚合需求给出可解释推荐 → 用户查看主推荐与备选区域 → 定位座位并预约。

目标：

- 所有“今天”均按 `Asia/Shanghai` 动态生成，只允许预约当天。
- 座位地图反映选定时段的实际预约占用，而不是只显示静态种子状态。
- 推荐结果真正受到场景、空位和同方向需求影响，并公开三个评分因素。
- 输出一个主推荐和最多两个备选，避免单点推荐在满座时失效。
- 使用真实学习意图数据，同时允许可说明的演示基线保证空数据场景可展示。
- 在不迁移数据库结构、不重做整体视觉的前提下完成可测试升级。

## 2. 非目标

本轮不实现：

- 跨日预约、日历选日或未来日期排班。
- 新的数据库表或迁移。
- 精确到个人的位置追踪或用户画像。
- 图书馆员后台、完整签到/离座超时流程。
- 借阅数据重构、社区治理或主页面的大规模组件拆分。
- 机器学习模型；本轮采用透明、可复现的规则评分。

## 3. 方案选择

采用“提取可测试领域模块”的方案，而不是继续在大型页面和路由中直接堆逻辑，也不在本轮引入完整的数据库归一化系统。

原因：

- 能让时间、座位状态和推荐排名以纯函数测试，降低演示期间的边界错误。
- 改动范围仍然可控，不需要数据库迁移。
- 为赛后扩展签到、动态容量和管理员配置保留清晰接口。

## 4. 架构与模块

### 4.1 时间领域 `lib/library/time.ts`

职责：

- 定义唯一时区 `Asia/Shanghai`。
- 定义系统允许的三个时段：`08:30—12:00`、`14:30—18:00`、`18:00—21:30`。
- 根据可注入的 `Date` 生成上海当天的 `YYYY-MM-DD`。
- 生成界面标签，例如 `今天 · 8月23日`。
- 校验请求日期是否为上海当天、时段是否属于允许集合。

所有 API 和客户端默认日期均从该模块的同一规则派生，避免各处自行拼接日期。

### 4.2 有效座位状态 `lib/seats/availability.ts`

公开状态：

- `free`：当前时段可预约。
- `using`：静态状态为使用中。
- `away`：静态状态为暂离。
- `reserved`：静态可用，但当前日期和时段已有有效预约。

优先级规则：静态 `using` 或 `away` 保留原状态；静态 `free` 且存在当前时段有效预约时变为 `reserved`；否则为 `free`。

该模块只负责确定有效状态和汇总区域容量，不直接访问数据库。

### 4.3 推荐引擎 `lib/study-match/engine.ts`

引擎接收：

- 用户学习目的和主题。
- 12 个楼层/区域候选的场景画像。
- 每个候选在当前时段的 `freeSeats` 与 `totalSeats`。
- 每个候选的真实匿名聚合意图数。
- 按时段和区域配置的演示基线数。

引擎返回按分数排序的候选，不访问数据库、不依赖系统当前时间。

12 个区域都具有显式场景画像，例如安静度、协作适合度、设备便利、阅读氛围等。用户目的和主题先映射为场景需求，再与区域画像计算 `0–100` 的场景适配指标。

## 5. 评分规则与解释

总分为三个贡献分之和，最高 100 分：

```text
总分 = 场景适配贡献 + 时段空位贡献 + 同方向需求贡献

场景适配贡献 = 场景适配指标 × 50%
时段空位贡献 = (freeSeats / totalSeats) × 30
同方向需求贡献 = min(聚合需求人数 / 10, 1) × 20
```

规则：

- `totalSeats = 0` 或 `freeSeats = 0` 的候选不参与推荐。
- 聚合需求人数由真实意图人数与演示基线相加，但基线是否参与必须在结果中显式标记。
- 同方向需求封顶为 10 人，防止人气区域无限挤压场景适配和可用性。
- 分数相同时依次比较空位贡献、场景适配贡献、稳定的楼层/区域编号，保证测试和演示结果可复现。
- 若所有区域无空位，返回明确的“当前时段暂无可推荐区域”，不回退到满座区域。

返回的 `factors` 是三个已经加权的贡献分，三者相加等于 `score`。界面可直接展示为“场景 +42 / 空位 +24 / 同伴 +12”。

## 6. 演示基线与隐私

真实需求来自已有 `study_intents`，仅按日期、时段、推荐楼层和区域进行匿名聚合，不在推荐结果中暴露个人身份或精确座位。

演示基线用于新环境没有足够历史数据时维持可观察的区域差异：

- 基线以静态配置存在于推荐领域模块中，不伪装成真实用户。
- 只参与区域级人数指标，不产生虚构账号或数据库记录。
- 只要候选人数包含非零基线，`includesDemoBaseline` 就为 `true`。
- 界面显示“含演示基线”，讲解时明确这是赛事演示数据。

## 7. API 设计

### 7.1 `GET /api/seats`

必填查询参数：

- `floor`
- `bookingDate`：必须等于上海当天。
- `timeSlot`：必须属于三个允许时段。

服务端读取楼层座位，并检查同一日期、时段的有效预约，为每个座位返回有效状态。缺失或非法日期/时段返回 `400`。

响应继续包含座位数组，并补充请求上下文和生成时间，使客户端能确认当前展示的日期和时段。

### 7.2 `POST /api/reservations`

在原有鉴权、座位存在性和唯一约束之外：

- 使用共享时间模块验证上海当天和允许时段。
- 写入前再次查询目标座位在该日期/时段是否已有有效预约。
- 冲突返回 `409`，非法日期/时段返回 `400`。
- 数据库唯一约束仍作为并发冲突的最终保护。

### 7.3 `GET/POST /api/study-intent`

请求上下文包含当天日期和时段。POST 保存用户意图并运行推荐；GET 对已有意图按当前时段重新计算，避免返回过期的固定区域。

成功响应保留现有的 `intent` 外层包装，以便客户端恢复用户已选的目的和主题：

```ts
type StudyIntentResponse = {
  intent: {
    purpose: StudyPurpose;
    topic: StudyTopic | null;
    recommendation: Candidate;
    alternatives: Candidate[];
    generatedAt: string;
  } | null;
};

type Candidate = {
  floor: number;
  zone: string;
  zoneName: string;
  score: number;
  freeSeats: number;
  totalSeats: number;
  peerCount: number;
  includesDemoBaseline: boolean;
  factors: {
    sceneFit: number;
    availability: number;
    peerDemand: number;
  };
  reason: string;
};
```

`recommendation` 为第一名，`alternatives` 最多两个。没有可用候选时返回具有明确错误码和中文提示的业务错误，不制造结果。

## 8. 客户端数据流

1. `SeatsView` 按上海时区生成当天日期，选择默认时段。
2. 页面加载、楼层变化或时段变化时请求 `/api/seats`。
3. 用户提交学习意图时请求 `/api/study-intent`，显示主推荐和两个备选。
4. 点击候选区域时切换对应楼层并定位区域，然后重新读取该楼层当前时段座位。
5. 页面可见期间每 15 秒刷新当前楼层座位和已有推荐。
6. 参数变化时中止上一条未完成请求，避免慢响应覆盖新时段数据。
7. 预约成功后立即刷新座位与推荐，使 `reserved` 状态和空位分数同步变化。

## 9. 界面设计

沿用现有视觉语言和页面结构：

- 日期文案改为动态 `今天 · M月D日`。
- 座位图图例增加“已预约”，并显示当前时段。
- 增加轻量的“更新于 HH:mm:ss”状态。
- 主推荐卡显示区域、综合分、空位、同方向人数和三个贡献分。
- 两个备选使用紧凑卡片，支持“定位此区域”。
- 包含演示基线时显示清晰的小标签或说明。
- 自动刷新失败时保留上一版有效内容，仅显示轻量提示；成功后提示自动消失。
- 所有区域满座时显示空状态和切换时段建议。

不新增复杂图表，不改变全局导航，不为本轮功能重构整页。

## 10. 错误与并发处理

- 客户端发送前和服务端接收后都校验日期与时段，服务端结果为准。
- 日期跨过上海午夜后，下一次刷新更新为新的当天日期；旧日期请求将被服务端拒绝，客户端随即用新日期重试。
- 每类可刷新请求使用 `AbortController`，时段或楼层改变时取消旧请求。
- 自动刷新失败不清空已有地图或推荐，避免网络抖动破坏演示。
- 预约使用“预检查 + 数据库唯一约束”处理竞争；唯一约束冲突统一转成 `409`。
- 推荐计算只使用当前请求对应的座位快照和聚合快照，响应附带 `generatedAt` 便于识别新旧。

## 11. 测试策略

按照测试驱动开发顺序，先写失败测试，再实现：

### 11.1 时间测试

- 注入固定 UTC 时间，验证上海当天日期和中文标签。
- 验证上海午夜边界。
- 验证仅当天合法、三个时段合法。

### 11.2 座位状态测试

- 静态空闲且无预约保持 `free`。
- 静态空闲且有当前时段预约变为 `reserved`。
- `using` 和 `away` 不被预约标记覆盖。
- 不同日期或时段的预约不影响当前快照。
- 区域汇总只把 `free` 计为可用。

### 11.3 推荐引擎测试

- 场景适配、空位率或聚合需求变化会按权重改变排名。
- 满座和零容量候选被排除。
- 返回主推荐和最多两个备选。
- 三个贡献分之和等于总分。
- 演示基线参与时标记正确，不参与时为 `false`。
- 相同输入产生稳定排序。
- 全部满座时返回明确的无候选结果。

### 11.4 回归验证

- 现有渲染测试继续通过。
- 新领域测试加入统一测试脚本。
- 运行范围内 ESLint、生产构建和全部 Node 测试。
- 若执行环境允许启动开发服务器，再验证座位读取、预约冲突和推荐接口的端到端主路径；若环境仍无法启动，不声明 API 运行时验证成功。

## 12. 完成标准

满足以下条件才视为本轮完成：

- 页面不再出现写死的 `2026-08-20` 或“今天 · 8月20日”。
- 座位读取必须带当天日期和合法时段，已有预约显示为 `reserved`。
- 推荐由 12 个候选画像、当前时段空位和匿名聚合需求共同计算。
- 主推荐、两个备选、三个贡献分和演示基线标识均可见。
- 楼层/时段改变立即刷新，页面可见时每 15 秒刷新，旧请求不会覆盖新请求。
- 不新增数据库迁移。
- 新旧测试、Lint 和生产构建全部通过，并保留实际命令输出作为完成证据。
